# Архитектура JARVIS

## Слои

```
┌───────────────────────── Electron ─────────────────────────┐
│ Renderer (React, sandbox)  ──IPC (узкий, типизированный)──▶ │
│ Preload (contextBridge)                                     │
│ Main: окно, CSP, safeStorage, IPC-валидация                 │
│   └─ JarvisCore  ← не зависит от Electron, тестируется целиком
│        ├─ ChatOrchestrator: модель → инструмент → политика → подтверждение → результат
│        ├─ ProviderManager → ChatProvider (Anthropic | Demo | …)
│        ├─ ToolRegistry (риск, домен, описание для подтверждения)
│        ├─ Security: policy · confirmation · audit · secrets · injection
│        └─ SQLite (node:sqlite): настройки, диалоги, память, журнал
└─────────────────────────────────────────────────────────────┘
```

Каталоги: `src/shared` (типы и IPC-контракт) · `src/core` (логика без Electron) · `src/main` ·
`src/preload` · `src/renderer` · `tests` · `scripts`.

`JarvisCore` не знает про окна — поэтому позже его можно запустить как фоновый сервис, серверный
процесс или шлюз для телефона (этап 9) с теми же политиками и журналом.

## Как добавлять возможности

* **Новый ИИ-провайдер** — реализовать `ChatProvider` (`stream(req, signal)`), подключить в `ProviderManager`.
* **Новый инструмент** — `ToolRegistry.register({ name, risk, mutates, domain, inputSchema, describe, execute })`.
  Политика и подтверждение применяются автоматически; результаты внешних источников помечаются `external: true`.
* **Новая таблица** — добавить миграцию в конец `MIGRATIONS` (`src/core/db/database.ts`); старые не менять.
* **Новый экран** — компонент в `src/renderer/views`, методы — в `JarvisApi` (`src/shared/ipc.ts`) + обработчик в `src/main/ipc.ts`.

## Карта этапов и модулей

| # | Этап | Модуль (папка в `src/core`) | Ключевые решения |
|---|---|---|---|
| 1 | Ядро ✅ | `chat`, `db`, `providers`, `security`, `tools` | см. выше |
| 2 | Голос ✅ | `voice`, `shared/voice.ts`, `renderer/voice` | Интерфейсы `SpeechToText`/`TextToSpeech` (OpenAI-совместимые клиенты); запись и VAD в рендерере, распознавание в главном процессе (ключ не покидает его); слово «Джарвис» и «стоп» — чистый разбор текста; разрешение `media` только при `micEnabled`; озвучка: голоса Windows или API |
| 3 | Управление ПК ✅ (частично) | `computer` | Сделано: файлы в белом списке папок, запуск разрешённых программ, браузер (Playwright + Edge/Chrome, отдельный профиль), снимок экрана с подтверждением. Не сделано: Windows UI Automation (управление окнами чужих программ) |
| 4 | ИИ-программист ✅ | `dev`, `chat/executor.ts` | Свои инструменты поверх `ToolExecutor` + субагенты `developer/tester/reviewer` (`AgentRunner`, свой цикл модель→инструменты, ограниченные наборы инструментов). SDK можно подключить позже как ещё одного «исполнителя» за той же политикой |
| 5 | CRM ✅ | `crm` | Клиент к API «Сайберлос» (Node/Express/Prisma): отдельная учётная запись **read-only**, домен `training` по умолчанию; `production` — только чтение; отчёты: заявки, продажи, менеджеры, производство |
| 6 | ИИ-наставник ✅ | `mentor` | Таблицы: `kb_documents` (версия, статус «утверждено», источник), `courses`, `lessons`, `assignments`, `progress`, `employees`. Ответы только по утверждённой базе знаний с цитированием источника; интерактив — оверлей подсветки в UI CRM (скрипт-подсказчик, подключаемый к фронтенду CRM); задания — на тестовых данных; ошибки сотрудников → обучающее задание, **без санкций** |
| 7 | Телефония ✅ (каркас) | `telephony` | Провайдер (SIP/облачная АТС) за интерфейсом; перед звонком — проверка согласия и окна времени; в начале разговора — уведомление об ИИ; запись/расшифровка только при `consent.recording = true`; итоги в CRM (запись требует отдельного разрешения) |
| 8 | Автономные задачи ✅ | `scheduler`, `agents` | Планировщик (cron-выражения) + очередь задач в SQLite; каждый фон. запуск имеет бюджет шагов, таймаут и журнал; специализированные агенты; общий «Стоп» |
| 9 | Мобильный доступ ✅ | `gateway` | Отдельный сервер-шлюз (TLS, сопряжение по QR + устройство-ключ, токены с коротким сроком, список разрешённых команд). Телефон только ставит поручения; опасные действия подтверждаются на ПК или вторым фактором |

## Данные этапа 1 (SQLite, `jarvis.db`)

`settings(key,value)` · `conversations` · `messages(role: user|assistant|tool, content JSON-блоки)` ·
`memory(kind,content,source)` · `audit_log(…, prev_hash, hash)`.

## Принятые решения

* **Messages API вместо Agent SDK на этапе 1**: достаточно для чата и своих инструментов, где
  политика и подтверждения находятся в нашем коде. Agent SDK подключается на этапах 4/8 как один из
  «исполнителей» агентов — за теми же политиками.
* **`node:sqlite` вместо `better-sqlite3`**: нет нативной сборки под Electron/Windows. Минус — API
  экспериментальный; миграция на другой драйвер локализована в `src/core/db`.
* **Ядро отдельно от Electron**: полная тестируемость и переиспользование в сервере/шлюзе.

## Как устроены этапы 7, 9, 10 (по факту)

* **Телефония** (`src/core/telephony`): `policy.ts` (номера, окно времени, лимиты, маска) → `script.ts` (жёсткий сценарий: представление ИИ → согласие → урок → итог; «стоп»/«не звоните») → `service.ts` (реестр согласий, журнал `calls`, запись текста только при согласии) → `provider.ts` (интерфейс `TelephonyProvider`/`Line`; есть `SimulatorProvider`; настоящий оператор подключается новой реализацией и отдельным выключателем).
* **Шлюз** (`src/core/gateway`): `devices.ts` (устройства с хешем токена, одноразовый код, лимитер) + `server.ts` (HTTP на `node:http`, страница-PWA без внешних зависимостей, проверка Host и адреса клиента, CSP). Удалённая политика — в `ToolExecutor` (`ExecContext.remoteDevice`): high+ запрещено, подтверждения только при `gatewayAllowActions` и только на ПК.
* **Модули** (`src/core/modules.ts`): префикс имени инструмента → модуль; выключенный модуль не попадает модели и блокируется в исполнителе (на случай «галлюцинации» имени).
